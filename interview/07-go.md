## Chi tiết

### Ngôn ngữ

- [ ] Array và slice
  - Array `[4]int` là **giá trị**: gán hay truyền vào hàm là copy cả mảng. Độ dài là một phần của kiểu.
  - Slice là header 3 từ: con trỏ tới underlying array, `len`, `cap`. Truyền slice = copy header,
    vẫn trỏ cùng mảng.
  ```go
  a := []int{1, 2, 3, 4}
  b := a[:2]          // len 2, cap 4, chung mảng với a
  b = append(b, 99)   // còn cap → ghi đè a[2]
  // a == [1 2 99 4]
  ```
  - ⚠️ Hàm nhận slice rồi `append`: nếu vượt cap thì mảng mới, caller không thấy; nếu còn cap thì
    ghi đè dữ liệu caller. Trả slice mới về (`s = append(s, x)`).
  - ⚠️ Full slice expression `a[0:2:2]` giới hạn cap, buộc `append` cấp mảng mới.
  - ⚠️ Sub-slice nhỏ của mảng lớn (ví dụ 10 byte header của file 100 MB) giữ cả mảng lớn không được GC.
    Copy ra: `slices.Clone` (1.21) hoặc `copy`.
  - Hệ số tăng cap khi `append` là chi tiết implementation (thay đổi qua các bản); đừng dựa vào nó.
    Biết trước kích thước thì `make([]T, 0, n)`.

- [ ] Map
  - Hash table; `v, ok := m[k]` phân biệt "không có" và zero value.
  - ⚠️ Ghi đồng thời (hoặc đọc khi đang ghi) → runtime báo `fatal error: concurrent map writes`,
    **không recover được**. Dùng `sync.Mutex`/`RWMutex` bọc map, hoặc `sync.Map` (hợp với key ghi
    một lần đọc nhiều, hoặc các goroutine làm việc trên tập key rời nhau).
  - ⚠️ Nil map: đọc được (trả zero value), **ghi thì panic**. `var m map[string]int` phải `make`.
  - Thứ tự duyệt **cố ý ngẫu nhiên**. Cần thứ tự: lấy key ra, `slices.Sort`.
  - ⚠️ `m[k].field = 1` không compile (value không addressable); dùng `map[K]*T` hoặc gán lại cả struct.
  - Map không trả bộ nhớ khi `delete` nhiều; tạo map mới nếu cần. `clear(m)` (1.21).
  - Go 1.24 đổi implementation sang Swiss table (kiểm tra lại); ngữ nghĩa không đổi.

- [ ] String, byte, rune
  - `string` là chuỗi byte immutable (thường UTF-8). `len(s)` là **số byte**. `s[i]` là byte.
  - `for i, r := range s` duyệt theo **rune** (code point), `i` là vị trí byte.
  - `len("Việt")` là 6 (ệ chiếm 3 byte), `utf8.RuneCountInString` là 4.
  - ⚠️ Cắt `s[:n]` có thể cắt giữa ký tự nhiều byte. Cắt theo rune: `[]rune(s)[:n]`.
  - `[]byte(s)` và `string(b)` copy dữ liệu. Nối nhiều lần: `strings.Builder`.
  - Chuẩn hoá Unicode (NFC/NFD) cho tiếng Việt: `golang.org/x/text/unicode/norm`. Xem
    [22-practical-data.md](22-practical-data.md).

- [ ] Value vs pointer receiver
  - Pointer receiver khi: method sửa receiver, struct lớn, struct chứa `sync.Mutex` (không được copy),
    hoặc để nhất quán (một method pointer thì nên tất cả pointer).
  - Value receiver: type nhỏ, immutable (`time.Time`), map/func/chan.
  - ⚠️ Value receiver trên struct có mutex → mỗi lời gọi copy mutex, lock không có tác dụng. `go vet` bắt (copylocks).

- [ ] 🟡 Method set
  - Method set của `T`: các method value receiver. Của `*T`: cả value và pointer receiver.
  - Hệ quả: nếu `Save()` có pointer receiver thì `T` **không** thoả interface có `Save()`, chỉ `*T` thoả.
  - Gọi `v.Save()` trên biến addressable vẫn được (Go tự lấy `&v`), nhưng gán `var i Saver = v` thì không.

- [ ] Interface
  - Thoả ngầm: có đủ method là thoả, không cần `implements`. Interface do **phía dùng** định nghĩa.
  - Interface nhỏ: `io.Reader`, `io.Writer`, `fmt.Stringer`, `error`. Ghép: `io.ReadWriter`.
  - "Accept interfaces, return structs": hàm nhận interface để linh hoạt và dễ mock, trả kiểu cụ thể.
  - Type assertion `v, ok := i.(T)`, type switch. `any` = `interface{}`.
  - Kiểm tra lúc compile: `var _ Saver = (*Repo)(nil)`.

- [ ] ⚠️ Nil interface trap
  - Interface là cặp (type, value). Chỉ `nil` khi **cả hai** đều nil.
  ```go
  func find() error {
      var e *MyErr = nil
      return e            // interface (type=*MyErr, value=nil) != nil
  }
  if err := find(); err != nil { /* luôn vào đây */ }
  ```
  - Sửa: trả `nil` tường minh khi không có lỗi; đừng khai báo biến kiểu con trỏ lỗi cụ thể rồi trả về.

- [ ] Embedding
  - Nhúng struct: field và method được **promote** lên struct ngoài. Là composition, không phải kế thừa.
  - ⚠️ Không có dynamic dispatch kiểu override: method của struct nhúng gọi method khác thì gọi bản của
    chính nó, không phải bản "override" ở struct ngoài.
  - Nhúng interface vào struct: thoả interface nhưng method chưa implement sẽ panic nil khi gọi
    (hay dùng trong test để implement một phần).
  - ⚠️ Nhúng `sync.Mutex` công khai làm `Lock()` lộ ra API của struct; thường đặt field tên `mu`.

- [ ] Error handling
  - Error là giá trị: `if err != nil { return fmt.Errorf("load user %d: %w", id, err) }`.
  - `%w` wrap để giữ chuỗi nguyên nhân; `%v` chỉ lấy chuỗi (cắt chuỗi, có chủ đích khi muốn ẩn lỗi nội bộ).
  - `errors.Is(err, sql.ErrNoRows)`: so theo chuỗi wrap (sentinel). `errors.As(err, &target)`: lấy
    kiểu cụ thể trong chuỗi.
  - Sentinel (`io.EOF`, `var ErrNotFound = errors.New(...)`): đơn giản, nhưng tạo coupling API.
    Custom type (`type ValidationError struct{...}`): mang dữ liệu.
  - Go 1.20: `errors.Join(e1, e2)`, `fmt.Errorf` nhiều `%w`, `Unwrap() []error`.
  - ⚠️ Không so chuỗi `err.Error() == "..."`. ⚠️ Không vừa log vừa return (log trùng nhiều tầng);
    xử lý ở một chỗ. ⚠️ Bỏ qua error bằng `_` phải có lý do.

- [ ] `panic`/`recover`
  - Dùng cho lỗi lập trình hoặc trạng thái không thể tiếp tục; không dùng thay error.
  - `recover()` chỉ có tác dụng khi gọi **trực tiếp trong hàm deferred** của cùng goroutine.
  - ⚠️ Panic trong goroutine không có recover → **cả process chết**. `net/http` recover panic trong
    handler, nhưng goroutine bạn tự `go` trong handler thì không được bảo vệ.
  - Fatal error runtime (concurrent map write, hết bộ nhớ) không recover được.

- [ ] `defer`
  - Chạy khi hàm return, thứ tự LIFO.
  - Tham số của lời gọi deferred được **tính ngay** tại dòng `defer`:
    `defer fmt.Println(i)` in giá trị `i` lúc đó.
  - Sửa được named return: `defer func() { if err != nil { err = fmt.Errorf("x: %w", err) } }()`.
  - ⚠️ `defer f.Close()` trong vòng lặp mở 10.000 file: chỉ đóng khi **hàm** kết thúc → hết file
    descriptor. Tách thân vòng lặp thành hàm riêng.
  - ⚠️ `defer f.Close()` bỏ qua lỗi `Close` khi ghi file; với file ghi nên kiểm tra lỗi close.

- [ ] 🟡 Generics (1.18+)
  - `func Map[T, U any](s []T, f func(T) U) []U`. Constraint là interface: `comparable`, `any`,
    `cmp.Ordered` (1.21), union `~int | ~string` (`~` gồm cả kiểu có underlying type đó).
  - Package `slices`, `maps`, `cmp` (1.21).
  - Giới hạn: method không có type parameter riêng; không specialization.
  - Khi nào dùng: container, thuật toán dùng chung trên nhiều kiểu. Khi nào không: chỉ có một kiểu,
    hoặc interface thường đã đủ.

- [ ] ⚠️ Biến vòng lặp (Go 1.22)
  - Trước 1.22: biến `for i := ...` và `for _, v := range` dùng **chung** qua các vòng. Goroutine/closure
    bắt `v` thấy giá trị cuối; `&v` trỏ cùng một địa chỉ.
  - Từ 1.22: mỗi vòng có biến riêng. Áp dụng theo dòng `go` trong `go.mod` của module (module khai báo
    `go 1.21` vẫn theo ngữ nghĩa cũ).
  - Go 1.22 còn có `for i := range 10`; Go 1.23 có range over function (iterator `iter.Seq`).

- [ ] Zero value
  - Mọi kiểu có zero value dùng được: `sync.Mutex{}`, `bytes.Buffer{}`, `strings.Builder{}` dùng ngay.
  - Nil slice vs empty slice: đều `len 0`, `append` được; ⚠️ JSON: nil → `null`, `[]T{}` → `[]`.
    API trả mảng nên khởi tạo rỗng.

- [ ] 🟡 Escape analysis
  - Compiler quyết định biến nằm stack hay heap. Trả con trỏ tới biến local là **an toàn** (biến được
    chuyển lên heap).
  - Xem: `go build -gcflags=-m`. Nguyên nhân escape: trả con trỏ, gán vào interface, closure bắt biến,
    slice kích thước không biết lúc compile.
  - Heap allocation tăng áp lực GC. Tối ưu chỉ khi profile chỉ ra hotspot.

### Concurrency

- [ ] Goroutine
  - Hàm chạy đồng thời, do runtime lập lịch. Stack khởi đầu vài KB, tự giãn; tạo hàng trăm nghìn được.
  - ⚠️ `go f()` không có cách lấy kết quả hay lỗi; phải thiết kế kênh trả về (channel, errgroup).
  - ⚠️ `main` return thì mọi goroutine chết, không chờ.

- [ ] 🟡 Scheduler G-M-P
  ```text
  G = goroutine    M = OS thread    P = processor logic (số lượng = GOMAXPROCS)
  Mỗi P có local run queue; M phải giữ một P mới chạy G.
  P hết việc → lấy từ global queue hoặc steal một nửa queue của P khác.
  G gọi syscall blocking → M bị giữ, P được trao cho M khác chạy tiếp.
  I/O mạng → netpoller (epoll/kqueue), G được park, không chiếm thread.
  ```
  - Preemption bất đồng bộ từ Go 1.14: vòng lặp chặt không gọi hàm cũng bị ngắt được.

- [ ] Channel
  | Thao tác | nil channel | channel mở | channel đã đóng |
  |---|---|---|---|
  | Gửi | Block mãi | Block tới khi có người nhận/còn chỗ buffer | **panic** |
  | Nhận | Block mãi | Block tới khi có dữ liệu | Trả zero value ngay, `ok = false` |
  | `close` | **panic** | OK | **panic** |
  - Unbuffered: gửi và nhận gặp nhau (đồng bộ, handoff). Buffered: gửi không block khi còn chỗ.
  - Quy ước: **bên gửi** đóng channel, và chỉ khi cần báo "hết dữ liệu" (`range ch`). Không bắt buộc
    đóng để GC.
  - Nhiều bên gửi: dùng `WaitGroup` rồi một goroutine đóng sau `wg.Wait()`.
  - ⚠️ Nil channel trong `select` không bao giờ được chọn → dùng để tắt một case.
  - Buffer không phải cách sửa deadlock; kích thước buffer nên có lý do (giới hạn đồng thời, hấp thụ burst).

- [ ] `select`
  - Chờ nhiều channel; nhiều case sẵn sàng thì chọn **ngẫu nhiên**. `default` → không block.
  - Timeout: `case <-time.After(d)` hoặc `ctx.Done()`.
  - ⚠️ `time.After` trong vòng lặp nóng: trước Go 1.23 timer không được thu hồi tới khi hết hạn. Dùng
    `time.NewTimer` + `Stop`, hoặc context.

- [ ] Package `sync`
  - `Mutex`: không reentrant (lock hai lần trong cùng goroutine là deadlock), không được copy sau khi dùng.
  - `RWMutex`: nhiều reader hoặc một writer; chỉ lợi khi đọc chiếm đa số và đoạn đọc đủ dài.
  - `WaitGroup`: ⚠️ `Add` **trước** khi `go`, không phải bên trong goroutine.
  - `Once`: khởi tạo lười an toàn. `OnceFunc`, `OnceValue` (1.21).
  - 🟡 `Pool`: tái dùng object tạm (buffer) để giảm allocation. ⚠️ Object có thể bị xoá ở GC bất cứ lúc
    nào; phải reset trước khi `Put`; không dùng làm connection pool.
  - 🟡 `sync/atomic`: `atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]` (1.19). Cho counter, cờ.
    Nhiều biến cần nhất quán với nhau → mutex.

- [ ] `context`
  - Truyền huỷ, deadline và giá trị gắn với request qua cây lời gọi.
  - `WithCancel`, `WithTimeout`, `WithDeadline`; ⚠️ luôn `defer cancel()` để giải phóng timer/goroutine.
  - `ctx.Err()` là `context.Canceled` hoặc `context.DeadlineExceeded`. Go 1.20+: `WithCancelCause`;
    1.21+: `WithoutCancel`, `AfterFunc`.
  - Quy ước: tham số đầu tiên `ctx context.Context`; không lưu context trong struct; không truyền `nil`
    (dùng `context.TODO()`).
  - ⚠️ `WithValue` chỉ cho dữ liệu gắn với request (request ID, trace, user đã xác thực). Không truyền
    tham số tuỳ chọn hay dependency. Key là kiểu unexported để tránh va chạm.
  - ⚠️ Context bị huỷ chỉ có tác dụng khi code **kiểm tra** nó (`select` trên `ctx.Done()`, hàm
    thư viện nhận ctx). Vòng lặp CPU không kiểm tra thì vẫn chạy.
  - ⚠️ Goroutine nền (gửi mail sau khi trả response) dùng ctx của request sẽ bị huỷ khi request xong.

- [ ] 🟡 `errgroup` (`golang.org/x/sync/errgroup`)
  ```go
  g, ctx := errgroup.WithContext(ctx)
  g.SetLimit(10)
  for _, id := range ids {
      g.Go(func() error { return fetch(ctx, id) })
  }
  if err := g.Wait(); err != nil { return err } // lỗi đầu tiên; ctx bị huỷ cho các goroutine còn lại
  ```

- [ ] Pattern
  - Worker pool: N goroutine đọc từ một channel job, giới hạn đồng thời (ví dụ tối đa 20 request tới API đối tác).
  - Fan-out: nhiều worker đọc một channel. Fan-in: gộp nhiều channel vào một.
  - Pipeline: chuỗi stage nối bằng channel, mỗi stage một (hoặc nhiều) goroutine; mọi stage phải
    thoát được khi ctx huỷ.
  - Semaphore đơn giản: `sem := make(chan struct{}, n)`.

- [ ] ⚠️ Goroutine leak
  - Goroutine block mãi: gửi vào channel không ai nhận (người nhận đã return vì timeout), chờ channel
    không bao giờ đóng, HTTP call không timeout.
  - Ví dụ kinh điển: hàm tạo goroutine gửi kết quả vào unbuffered channel, rồi `select` timeout return
    trước → goroutine kẹt mãi. Sửa: channel buffer 1, hoặc goroutine cũng `select` trên `ctx.Done()`.
  - Phát hiện: metric `runtime.NumGoroutine()` tăng dần, pprof goroutine profile, `goleak` trong test.

- [ ] Data race và `-race`
  - Race detector phát hiện truy cập đồng thời không đồng bộ **khi nó thực sự xảy ra** trong lúc chạy;
    không chứng minh code không có race.
  - Tốn CPU và RAM gấp nhiều lần; chạy trong test/CI, không bật production.
  - ⚠️ "Race lành tính" không tồn tại trong Go memory model; đọc/ghi `int` không đồng bộ vẫn là bug.

### Runtime

- [ ] 🟡 GC
  - Concurrent, tri-color mark-and-sweep, không chia thế hệ, không compact. Pause ngắn; đổi lại tốn
    CPU chạy song song với app, và có write barrier khi đang mark.
  - `GOGC` (mặc định 100): GC chạy khi heap tăng thêm 100% so với live heap sau lần GC trước.
    Tăng `GOGC` = ít GC hơn, tốn RAM hơn.
  - `GOMEMLIMIT` (1.19+): soft limit tổng bộ nhớ; GC chạy dày hơn khi gần limit. Đặt thấp hơn limit
    container một chút. ⚠️ Live heap vượt limit → GC chạy liên tục (thrash), CPU cao.
  - Giảm áp lực GC: ít allocation (tái dùng buffer, `sync.Pool`, pre-allocate slice), ít con trỏ.

- [ ] 🟡 pprof và trace
  - `import _ "net/http/pprof"` mở `/debug/pprof/`. ⚠️ Không expose ra internet; chạy trên port nội bộ.
  - Profile: `profile` (CPU), `heap` (`inuse_space` để tìm leak, `alloc_space` để tìm chỗ allocate nhiều),
    `goroutine` (tìm leak, xem đang kẹt ở đâu), `block`, `mutex` (phải bật bằng `runtime.SetBlockProfileRate`/
    `SetMutexProfileFraction`).
  - `go tool pprof -http=:8080 <url hoặc file>`: flame graph, top.
  - `go tool trace`: xem scheduler, GC, goroutine theo thời gian (latency, contention).

- [ ] 🔴 `GOMAXPROCS` trong container
  - Mặc định bằng số CPU. Trước Go 1.25, runtime **không** đọc CPU limit của cgroup: pod limit 2 CPU
    trên node 64 core có `GOMAXPROCS=64` → nhiều thread tranh nhau quota, bị CFS throttle, latency tăng.
    Cách xử lý phổ biến: `go.uber.org/automaxprocs` hoặc đặt biến môi trường.
  - Go 1.25 đã cho `GOMAXPROCS` mặc định theo CPU limit của cgroup (kiểm tra lại theo phiên bản bạn dùng).
  - Tương tự với memory: đặt `GOMEMLIMIT` theo limit container. Xem [19-devops-cloud.md](19-devops-cloud.md).

### Hệ sinh thái backend

- [ ] `net/http`
  - `type Handler interface { ServeHTTP(ResponseWriter, *Request) }`; `http.HandlerFunc` biến hàm thành Handler.
  - Mỗi request một goroutine. ⚠️ Handler dùng chung state phải đồng bộ.
  - Middleware: `func(next http.Handler) http.Handler`.
  - Go 1.22 `ServeMux`: `mux.HandleFunc("GET /users/{id}", h)`, `r.PathValue("id")`.
  - ⚠️ Ghi header sau khi đã `Write` body không có tác dụng; `WriteHeader` gọi hai lần sinh cảnh báo.

- [ ] ⚠️ Timeout
  - `http.Server` zero value **không có timeout**: client chậm (slowloris) giữ kết nối mãi.
    ```go
    srv := &http.Server{
        Addr: ":8080", Handler: mux,
        ReadHeaderTimeout: 5 * time.Second, ReadTimeout: 10 * time.Second,
        WriteTimeout: 15 * time.Second, IdleTimeout: 60 * time.Second,
    }
    ```
  - `http.DefaultClient` và `http.Get` **không có timeout**: API đối tác treo → goroutine và kết nối kẹt mãi.
    Tạo `&http.Client{Timeout: ...}` một lần, dùng lại (client giữ connection pool), kết hợp ctx theo request.
  - ⚠️ Luôn `defer resp.Body.Close()`; đọc hết body (`io.Copy(io.Discard, resp.Body)`) để connection được
    tái dùng. Kiểm tra `resp.StatusCode`, lỗi 4xx/5xx không trả `err`.
  - `Transport.MaxIdleConnsPerHost` mặc định 2: gọi nhiều tới cùng một host thì mở kết nối mới liên tục,
    nên tăng lên.

- [ ] Graceful shutdown
  ```go
  ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
  defer stop()
  go func() {
      if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) { log.Fatal(err) }
  }()
  <-ctx.Done()
  shutdownCtx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
  defer cancel()
  _ = srv.Shutdown(shutdownCtx) // ngừng nhận mới, chờ request đang chạy
  ```
  - Thêm: dừng consumer/worker, flush log/trace, đóng DB. Kubernetes: readiness fail trước, chờ LB
    ngừng gửi, `terminationGracePeriodSeconds` lớn hơn timeout shutdown.

- [ ] `database/sql`
  - `*sql.DB` là **pool**, an toàn dùng đồng thời, tạo một lần cho cả app. `sql.Open` chưa kết nối;
    `PingContext` để kiểm tra.
  - Cấu hình: `SetMaxOpenConns` (mặc định 0 = không giới hạn ⚠️), `SetMaxIdleConns` (mặc định 2),
    `SetConnMaxLifetime`, `SetConnMaxIdleTime`. Tổng max open × số instance phải nhỏ hơn giới hạn DB.
  - ⚠️ `rows, err := db.Query(...)` phải `defer rows.Close()`, kiểm tra `rows.Err()` sau vòng lặp.
    Quên close → connection không trả về pool → pool cạn, request treo.
  - `QueryRow().Scan()` trả `sql.ErrNoRows` khi không có dòng. NULL: `sql.NullString` hoặc con trỏ.
  - Transaction: `tx` gắn với một connection; ⚠️ trong transaction dùng `tx.Query`, không dùng `db.Query`
    (chạy ngoài transaction, có thể deadlock khi pool nhỏ). `defer tx.Rollback()` an toàn sau `Commit`.
  - Luôn dùng biến thể `...Context`. Placeholder theo driver (`?` MySQL, `$1` Postgres).
  - Thư viện: `sqlx`, `sqlc` (sinh code từ SQL), `pgx` (Postgres), GORM (ORM).

- [ ] JSON
  - Tag: `json:"name"`, `json:"name,omitempty"`, `json:"-"`, `json:",string"`.
  - Chỉ field **exported** (viết hoa) được encode/decode.
  - ⚠️ `omitempty` không bỏ struct zero value (như `time.Time{}`); Go 1.24 có `omitzero` (kiểm tra lại).
  - ⚠️ Decode số vào `any`/`map[string]any` thành `float64` → mất chính xác với ID lớn. Dùng
    `Decoder.UseNumber()` hoặc struct có kiểu.
  - `Decoder.DisallowUnknownFields()` cho API strict. Giới hạn kích thước body (`http.MaxBytesReader`).

- [ ] Project layout
  - `cmd/<app>/main.go` cho từng binary; `internal/` được compiler **cấm** import từ ngoài module
    cha; `pkg/` là quy ước gây tranh cãi, không bắt buộc.
  - Repo "golang-standards/project-layout" **không** phải chuẩn chính thức.
  - Chia package theo domain (`order`, `payment`), tránh package `utils`/`common`/`models` chung chung.
  - ⚠️ Import vòng giữa package là lỗi compile → buộc thiết kế phụ thuộc một chiều.

- [ ] Go module
  - `go.mod`: module path, phiên bản Go, dependency. `go.sum`: checksum để xác minh, commit cả hai.
  - Minimal version selection: chọn phiên bản **thấp nhất** thoả mọi yêu cầu → build tái lập mà không
    cần lock file riêng.
  - Major version ≥ 2 đổi import path: `example.com/lib/v2`.
  - `go mod tidy`, `replace` (dev local), `GOPROXY`, `GOPRIVATE` (repo nội bộ), `go mod vendor`.
  - Directive `toolchain` (1.21+).

## Senior trả lời khác gì

| Câu hỏi | Junior/mid | Senior |
|---|---|---|
| Channel hay mutex? | "Go khuyên dùng channel." | Channel để chuyển quyền sở hữu dữ liệu/điều phối luồng việc; mutex để bảo vệ state dùng chung. Mutex quanh một map thường đơn giản và nhanh hơn một goroutine quản lý map qua channel. |
| Làm sao tránh goroutine leak? | "Nhớ đóng channel." | Mọi goroutine phải có đường thoát: ctx, channel done, buffer đủ cho người gửi; timeout mọi I/O; theo dõi `NumGoroutine`, pprof goroutine; `goleak` trong test. |
| Service Go dùng quá nhiều RAM trong k8s | "Tăng limit." | Xem heap profile `inuse_space`, tìm sub-slice giữ mảng lớn, map không co lại; đặt `GOMEMLIMIT`; kiểm tra `GOMAXPROCS` và số goroutine. |
| Gọi API ngoài bị treo | "Thêm retry." | `http.Client` mặc định không timeout; đặt timeout + ctx theo request; đóng và drain body; tăng `MaxIdleConnsPerHost`; retry có backoff + jitter chỉ với lỗi tạm thời và request idempotent. |
| Xử lý error thế nào cho tốt? | "`if err != nil { return err }`." | Wrap với ngữ cảnh bằng `%w`, sentinel/custom type cho lỗi caller cần phân nhánh, map lỗi sang HTTP status ở biên, log một lần ở chỗ xử lý. |

## Tình huống

1. **Service chạy vài ngày thì RAM tăng dần, số goroutine tăng theo.**
   - Gợi ý: pprof goroutine xem kẹt ở đâu (send channel, `net/http` read, lock); tìm HTTP client không
     timeout, goroutine chờ channel sau timeout; sửa bằng ctx và buffer.
2. **Sau khi deploy lên k8s với limit 2 CPU, p99 latency tăng gấp đôi so với chạy trên VM.**
   - Gợi ý: `GOMAXPROCS` bằng số core node, bị CFS throttle; kiểm tra metric throttling; automaxprocs
     hoặc Go 1.25+.
3. **Lỗi thỉnh thoảng `fatal error: concurrent map writes` và pod restart.**
   - Gợi ý: map dùng chung giữa handler không có lock; không recover được; thêm mutex hoặc tách state;
     chạy test với `-race` để tìm các chỗ khác.
4. **API trả `null` thay vì `[]` khiến mobile app crash.**
   - Gợi ý: nil slice encode thành `null`; khởi tạo `[]T{}`; thống nhất contract API; thêm test contract.
5. **Pool DB cạn, request treo dù traffic thấp.**
   - Gợi ý: quên `rows.Close()` ở nhánh return sớm; dùng `db` thay `tx` trong transaction; transaction
     không commit/rollback; xem `db.Stats()` (InUse, WaitCount).
6. **Hàm xử lý 1 file 100 MB, chỉ giữ 64 byte đầu cho mỗi file, nhưng RAM không giảm.**
   - Gợi ý: sub-slice giữ underlying array; copy ra slice mới.
