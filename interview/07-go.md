#### 1.1 Slice, map, string

**Vì sao cần học:** Slice và map là hai cấu trúc dùng nhiều nhất trong Go, và cũng là nguồn câu
hỏi vặn nhiều nhất. Người từ PHP hay coi slice như array PHP (sửa trong hàm không ảnh hưởng bên
ngoài), nên dính bug `append` ghi đè dữ liệu. Còn map ghi đồng thời thì làm crash cả service.

**Học gì**

*Array và slice*
- *Array* có kích thước cố định nằm ngay trong kiểu, ví dụ `[3]int`. Array là giá trị: gán hay
  truyền vào hàm là copy cả mảng.
- *Slice* (`[]int`) là cửa sổ nhìn vào một array nằm bên dưới, gọi là *backing array*. Bản thân
  slice chỉ là một *header* gồm 3 phần:
  - `ptr`: trỏ tới phần tử đầu tiên trong backing array.
  - `len`: số phần tử đang dùng.
  - `cap`: số phần tử tối đa trước khi phải cấp array mới.
- Truyền slice vào hàm là copy header, **không** copy dữ liệu. Hai header cùng trỏ một backing array.
- Đối chiếu PHP: array PHP được copy khi bị sửa (*copy-on-write*), nên hàm sửa array không ảnh
  hưởng caller. Slice của Go thì có ảnh hưởng.

*append*
- `append(s, x)` có hai trường hợp:
  - Còn cap: ghi `x` vào backing array chung, trả về header mới có `len + 1`.
  - Hết cap: cấp một array mới lớn hơn, copy dữ liệu sang, trả về header trỏ tới array mới.
- ⚠️ Từ đó sinh ra hai bẫy:
  - Còn cap: ghi đè dữ liệu của một slice khác đang dùng chung backing array.
  - Hết cap: hàm con `append` vào slice, nhưng caller vẫn giữ header cũ nên không thấy phần tử mới.

  ```go
  a := []int{1, 2, 3, 4}
  b := a[:2]          // b = [1 2], cap vẫn là 4
  b = append(b, 99)   // còn cap nên ghi vào a[2]: a thành [1 2 99 4]
  ```

- Luôn gán lại kết quả: `s = append(s, x)`.
- `a[i:j:k]` (*full slice expression*) đặt cap của slice mới bằng `k - i`. Nhờ vậy `append` sau đó
  bắt buộc phải cấp array mới, không ghi đè `a`.
- Hệ số tăng cap khi cấp array mới là chi tiết implementation, đừng dựa vào nó. Biết trước kích
  thước thì cấp sẵn: `make([]T, 0, n)`.
- ⚠️ Sub-slice nhỏ giữ cả backing array lớn. Ví dụ đọc file 100 MB rồi chỉ giữ lại 64 byte đầu:
  vẫn tốn 100 MB, vì GC không thu hồi được array. Copy phần cần giữ ra bằng `slices.Clone`.

*nil slice và empty slice*
- `var s []int` là *nil slice*, còn `s := []int{}` là *empty slice*. Cả hai đều có `len` bằng 0 và
  dùng `append`, `range` như nhau.
- ⚠️ Khác nhau khi encode JSON: nil slice thành `null`, empty slice thành `[]`.

*Map*
- Đọc kèm kiểm tra: `v, ok := m[k]`. Không có key thì `v` là *zero value* và `ok` là `false`.
  - *Zero value* là giá trị mặc định của mỗi kiểu: `0`, `""`, `false`, `nil`.
- ⚠️ *nil map* (khai `var m map[string]int` mà chưa `make`): đọc được, trả zero value. Ghi thì panic.
- Thứ tự duyệt bằng `range` bị cố ý làm ngẫu nhiên, để không ai viết code dựa vào nó. Khác array
  PHP luôn giữ thứ tự chèn.
- Từ Go 1.24, map được cài bằng *Swiss table* (một kiểu bảng băm nhanh hơn). Ngữ nghĩa không đổi.
- ⚠️ Nhiều goroutine cùng ghi vào một map: `fatal error: concurrent map writes`.
  - Đây là fatal error chứ không phải panic, nên **không recover được**. Process chết.
- ⚠️ `m[k].field = 1` với value là struct thì không compile, vì phần tử trong map không
  *addressable* (không lấy được địa chỉ). Lấy ra, sửa, rồi gán lại; hoặc lưu con trỏ `map[K]*T`.
- ⚠️ Map không co lại sau `delete`: map từng chứa một triệu key vẫn giữ phần bộ nhớ đó.

*String*
- String là chuỗi byte immutable, thường chứa UTF-8.
- `len(s)` đếm **byte**, không đếm ký tự, giống `strlen` của PHP. `len("Việt")` là 6, vì `ệ`
  chiếm 3 byte.
- `for i, r := range s` duyệt theo *rune* (một ký tự Unicode), với `i` là vị trí byte.
- ⚠️ `s[:n]` cắt theo byte nên có thể cắt giữa một ký tự, giống dùng `substr` với tiếng Việt.
- Nối chuỗi nhiều lần thì dùng `strings.Builder`, không dùng `+=` trong vòng lặp.

#### 1.2 Struct, method, interface

**Vì sao cần học:** Go không có class và không có kế thừa. Người từ PHP phải đổi cách nghĩ:
interface được thoả ngầm, còn tái dùng code thì bằng composition. Câu hỏi hay gặp: chọn pointer
hay value receiver, và interface nên khai ở đâu.

**Học gì**

*Method và receiver*
- Go có `struct` để chứa dữ liệu, và *method* gắn vào một kiểu qua *receiver*:

  ```go
  func (u User) Name() string      { return u.name }   // value receiver: nhận một bản copy
  func (u *User) Rename(n string)  { u.name = n }      // pointer receiver: sửa bản gốc
  ```

- Dùng pointer receiver khi:
  - Method cần sửa receiver.
  - Struct lớn, copy tốn.
  - Struct chứa `sync.Mutex`.
  - Để nhất quán: một method đã dùng pointer receiver thì các method khác cũng nên dùng.
- ⚠️ Value receiver trên struct có mutex: mỗi lần gọi method là copy luôn mutex, lock trên bản copy
  không bảo vệ được gì. `go vet` (phần kiểm tra copylocks) bắt được lỗi này.

*Interface*
- Interface trong Go được thoả **ngầm**: kiểu nào có đủ method là thoả, không cần viết `implements`.
- Vì vậy interface thường do **phía dùng** định nghĩa. Ví dụ service cần lưu user thì tự khai
  `type UserSaver interface { Save(User) error }`, chỉ gồm method nó cần. Ngược với PHP, nơi
  interface thường nằm cạnh class implement.
- Interface nên nhỏ, 1–2 method, như `io.Reader` hay `error`.
- Câu thành ngữ "accept interfaces, return structs": tham số nhận interface để linh hoạt, còn giá
  trị trả về là struct cụ thể.
- *Type assertion* `v, ok := x.(*MyErr)` lấy ra kiểu cụ thể. *Type switch*
  `switch v := x.(type)` rẽ nhánh theo kiểu.
- Bắt compiler kiểm tra một kiểu có thoả interface không: `var _ Saver = (*Repo)(nil)`.

*Embedding*
- *Embedding*: đặt một kiểu vào struct mà không đặt tên field. Field và method của nó được
  *promote*, tức gọi thẳng được từ struct bên ngoài:

  ```go
  type Base struct{}
  func (Base) Hello() string { return "base" }

  type Admin struct{ Base }   // Admin{}.Hello() gọi được
  ```

- Đây là composition, không phải kế thừa.
- ⚠️ Không có override: method của `Base` gọi một method khác thì luôn gọi bản của `Base`, kể cả
  khi `Admin` có method cùng tên. Khác `$this->method()` trong PHP, vốn gọi bản của class con.
- ⚠️ Nhúng `sync.Mutex` vào struct công khai làm lộ `Lock()` và `Unlock()` ra ngoài. Hãy đặt nó
  thành field có tên, thường là `mu`.

*Zero value dùng được ngay*
- Nhiều kiểu dùng được ngay ở zero value, không cần constructor: `sync.Mutex{}`, `bytes.Buffer{}`.

#### 1.3 Error, panic, defer

**Vì sao cần học:** Go không có exception. Mọi hàm có thể lỗi đều trả về `error`, nên xử lý lỗi
chiếm phần lớn code và là chỗ reviewer soi kỹ nhất. Đây là khác biệt lớn nhất so với try/catch của
PHP, và câu "error của Go khác exception thế nào" gần như luôn được hỏi.

**Học gì**

*Error là giá trị*
- Hàm trả lỗi như một giá trị bình thường, và caller kiểm tra ngay:

  ```go
  u, err := repo.Find(ctx, id)
  if err != nil {
      return fmt.Errorf("load user %d: %w", id, err)
  }
  ```

- *Wrap* là bọc lỗi gốc kèm thêm ngữ cảnh:
  - `%w` giữ lỗi gốc bên trong, để tầng trên vẫn kiểm tra được nguyên nhân.
  - `%v` chỉ ghép thành chuỗi, cắt đứt chuỗi nguyên nhân. Dùng có chủ đích khi muốn giấu lỗi nội bộ.
- Hai cách định nghĩa lỗi:
  - *Sentinel error*: một biến lỗi cố định, ví dụ `var ErrNotFound = errors.New("not found")`.
  - *Custom type*: struct implement `error`, mang thêm dữ liệu (field nào sai, mã lỗi).

*Kiểm tra lỗi*
- `errors.Is(err, ErrNotFound)`: so với sentinel, đi xuyên qua mọi lớp wrap. Tương tự
  `catch (NotFoundException $e)`.
- `errors.As(err, &target)`: tìm trong chuỗi wrap một lỗi có kiểu cụ thể và lấy nó ra.
  - Go 1.26 có bản generic `errors.AsType[T]`.
- `errors.Join` (1.20): gộp nhiều lỗi thành một.
- ⚠️ Không so `err.Error() == "..."`: ai đó sửa câu thông báo là code hỏng.
- ⚠️ Không vừa log vừa return. Mỗi tầng đều log thì một lỗi thành năm dòng log.
- ⚠️ Bỏ qua error bằng `_` phải có lý do rõ ràng.

*panic và recover*
- `panic` dừng hàm hiện tại và tháo ngược stack. Chỉ dùng cho lỗi lập trình (index vượt biên,
  trạng thái không thể xảy ra), không dùng như `throw`.
- `recover()` bắt panic, nhưng chỉ có tác dụng khi được gọi **trực tiếp** trong một hàm deferred
  (xem `defer` ngay dưới) của **cùng goroutine**.
- ⚠️ Panic trong một goroutine mà không được recover thì **chết cả process**.
  - `net/http` tự recover panic trong handler.
  - Goroutine bạn tự `go` thì không ai recover hộ.
  - Khác PHP-FPM, nơi một request lỗi không ảnh hưởng worker khác.

*defer*
- `defer f()` hẹn chạy `f` khi hàm hiện tại kết thúc, dù kết thúc bằng return hay panic. Vai trò
  như `finally`.
  - Nhiều `defer` chạy theo thứ tự ngược lại (LIFO).
  - Tham số của `f` được tính **ngay** tại dòng `defer`, không phải lúc `f` chạy.
  - `defer` sửa được *named return* (giá trị trả về có đặt tên trong chữ ký hàm).
- ⚠️ `defer f.Close()` trong vòng lặp mở hàng nghìn file: các file chỉ được đóng khi cả hàm kết
  thúc, nên hết file descriptor giữa chừng.
- ⚠️ Khi **ghi** file, `Close` có thể trả lỗi (dữ liệu chưa ghi được xuống). `defer f.Close()` bỏ
  qua lỗi đó.

*Đối chiếu PHP/Java*

| | Exception (PHP/Java) | Error value (Go) |
|---|---|---|
| Lan truyền | Nhảy ngầm qua nhiều tầng tới chỗ `catch` | Tường minh, trả qua từng tầng |
| Nhìn vào code | Không thấy dòng nào có thể ném | Mọi chỗ có thể lỗi đều hiện ra |
| Độ dài code | Ngắn | Dài dòng, `if err != nil` khắp nơi |
| Stack trace | Có sẵn | Không có mặc định, dựa vào thông điệp wrap |

#### 1.4 Goroutine, channel, sync cơ bản

**Vì sao cần học:** Concurrency là lý do chính người ta chọn Go, nên ngay vòng junior đã hỏi hành
vi của channel và `WaitGroup`. Với người từ PHP-FPM, đây là lần đầu viết code chạy song song trong
cùng một vùng nhớ, nên cần nắm chắc công cụ trước khi viết.

**Học gì**

*Goroutine*
- `go f()` chạy `f` đồng thời trên một *goroutine*: luồng chạy nhẹ do runtime của Go quản lý, không
  phải OS thread.
  - Stack khởi đầu chỉ vài KB và tự giãn khi cần.
  - Một process chạy được hàng trăm nghìn goroutine.
- So với PHP-FPM worker: worker là cả một process tốn hàng chục MB. Goroutine chỉ vài KB, và mọi
  goroutine dùng chung vùng nhớ của process.
- ⚠️ `go f()` không trả về kết quả hay lỗi. Muốn lấy kết quả phải qua channel, biến có lock, hoặc
  `errgroup` (module 2.2).
- ⚠️ `main` return thì mọi goroutine chết ngay, dù chưa làm xong.

*Channel*
- *Channel* là đường ống để các goroutine gửi và nhận giá trị: `ch <- v` là gửi, `v := <-ch` là nhận.
  - *Unbuffered* (`make(chan T)`): bên gửi phải chờ tới khi có bên nhận. Đây là một cú bàn giao
    đồng bộ (*handoff*).
  - *Buffered* (`make(chan T, 10)`): bên gửi không phải chờ khi buffer còn chỗ.
- Hành vi theo trạng thái của channel:

  | Thao tác | nil channel | channel mở | channel đã đóng |
  |---|---|---|---|
  | Gửi | Block mãi | Block tới khi có người nhận/còn buffer | **panic** |
  | Nhận | Block mãi | Block tới khi có dữ liệu | Zero value ngay, `ok = false` |
  | `close` | **panic** | OK | **panic** |

- ⚠️ Thêm buffer không phải cách sửa *deadlock* (các goroutine chờ nhau mãi), nó chỉ làm lúc bị kẹt đến muộn hơn.
- **Bên gửi** đóng channel, và chỉ đóng khi cần báo "hết dữ liệu" (để vòng `for v := range ch` của
  bên nhận kết thúc).

*select*
- `select` chờ nhiều thao tác channel cùng lúc và chạy case nào sẵn sàng trước:

  ```go
  select {
  case v := <-results:
      use(v)
  case <-time.After(time.Second):
      return errTimeout
  }
  ```

- Nhiều case cùng sẵn sàng thì chọn ngẫu nhiên một case.
- Có nhánh `default` thì `select` không block: không case nào sẵn sàng là chạy `default`.
- Gán channel của một case thành nil để tắt case đó, vì thao tác trên nil channel block mãi.

*sync cơ bản*
- `sync.Mutex`: khoá loại trừ.
  - Không reentrant: goroutine đang giữ lock mà gọi `Lock()` lần nữa là tự deadlock.
  - Không được copy sau khi đã dùng.
- `sync.RWMutex`: nhiều bên đọc cùng lúc được, ghi thì độc quyền.
- `sync.Once`: chạy một hàm đúng một lần. `sync.OnceValue` (1.21) chạy một lần và trả về giá trị.
- `sync.WaitGroup`: chờ một nhóm goroutine chạy xong.
  - ⚠️ Gọi `wg.Add(1)` **trước** lệnh `go`, không đặt bên trong goroutine. Nếu goroutine chưa kịp
    chạy, `Wait()` thấy bộ đếm bằng 0 và trả về sớm.
  - Go 1.25 có `wg.Go(func() { ... })`, gộp `Add`, `go` và `Done` làm một.
  - `go vet` từ 1.25 báo lỗi khi `Add` đặt sai chỗ.

*Channel hay mutex*
- Channel để chuyển quyền sở hữu dữ liệu hoặc điều phối công việc (giao việc, báo xong).
- Mutex để bảo vệ state dùng chung (counter, cache).

**Đọc**
- Effective Go: [Concurrency](https://go.dev/doc/effective_go#concurrency)
- Package [sync](https://pkg.go.dev/sync) (đọc [WaitGroup.Go](https://pkg.go.dev/sync#WaitGroup.Go))

#### 1.5 Testing cơ bản

**Vì sao cần học:** Go có sẵn công cụ test trong lệnh `go test`, không cần PHPUnit hay framework
ngoài. Table-driven test là idiom mà reviewer Go mong thấy, và hay được yêu cầu viết ngay trong
buổi live coding.

**Học gì**

*go test*
- File test có tên `xxx_test.go`, hàm test có dạng `func TestXxx(t *testing.T)`. Chạy mọi test
  trong module: `go test ./...`.
- `t.Errorf` báo lỗi rồi **chạy tiếp** test. `t.Fatalf` báo lỗi rồi **dừng** test đó ngay.
- Go không cần thư viện assertion kiểu `assertEquals`: viết thẳng `if got != want { t.Errorf(...) }`.

*Table-driven test*
- Khai một slice các case, lặp qua và chạy mỗi case thành một *subtest* bằng `t.Run`:

  ```go
  tests := []struct {
      name string
      in   string
      want int
  }{
      {"ascii", "abc", 3},
      {"tieng viet", "Việt", 4},
  }
  for _, tc := range tests {
      t.Run(tc.name, func(t *testing.T) {
          if got := utf8.RuneCountInString(tc.in); got != tc.want {
              t.Errorf("got %d, want %d", got, tc.want)
          }
      })
  }
  ```

- Lợi ích của `t.Run`:
  - Lỗi được báo kèm tên case.
  - Chạy riêng một case bằng `-run 'TestX/case_name'`.
- `t.Parallel()` cho các test hoặc subtest chạy song song.
- Đối chiếu PHP: data provider của PHPUnit gần giống table-driven test.

*Các helper của testing.T*
- `t.Helper()`: đánh dấu một hàm là helper, để lỗi được báo ở dòng gọi helper thay vì dòng bên trong nó.
- `t.Cleanup(fn)`: đăng ký việc dọn dẹp, chạy sau khi test xong.
- `t.TempDir()`: tạo thư mục tạm, tự xoá sau test.
- `t.Context()` (1.24): một context bị huỷ khi test xong.

*Test HTTP*
- `httptest.NewRecorder()`: gọi thẳng handler và ghi lại response, không cần mở port.
- `httptest.NewServer()`: chạy một server thật trên localhost, dùng để giả API đối tác.

*Black-box và white-box*
- Trong Go, tên viết hoa chữ đầu là *exported* (dùng được từ package khác), viết thường là
  *unexported* (chỉ dùng trong package).
- Test khai cùng package (`package user`): thấy cả phần unexported. Đây là *white-box*.
- Test khai package `user_test`: chỉ dùng được phần exported, như người dùng thật. Đây là *black-box*.

**Đọc**
- Package [testing](https://pkg.go.dev/testing) (mục [Subtests and Sub-benchmarks](https://pkg.go.dev/testing#hdr-Subtests_and_Sub_benchmarks))
- Wiki: [TableDrivenTests](https://go.dev/wiki/TableDrivenTests); Go blog: [Using Subtests and Sub-benchmarks](https://go.dev/blog/subtests)
- Package [net/http/httptest](https://pkg.go.dev/net/http/httptest)

**Nắm chắc khi**

- [ ] Test được một handler trả 404 và 200 bằng `httptest.NewRecorder`, không mở port

#### 1.6 Đối chiếu với PHP

**Vì sao cần học:** Người phỏng vấn thường hỏi "khác gì so với stack bạn đang dùng". Hiểu đúng khác
biệt mô hình runtime giúp tránh cả một nhóm bug mà PHP-FPM không bao giờ gặp.

**Học gì**

*Mô hình runtime*

| | PHP-FPM | Go |
|---|---|---|
| Process | Nhiều worker process | Một binary sống lâu |
| Đơn vị xử lý một request | Một worker process, hàng chục MB | Một goroutine, vài KB |
| Số request đồng thời | `pm.max_children` | Hàng chục nghìn trong một process |
| Sau khi request xong | Dọn sạch mọi biến (*share-nothing*) | Mọi biến vẫn còn |

- Hệ quả: biến package-level (khai ngoài mọi hàm, giống biến global hoặc static) và state trong
  struct **dùng chung** giữa các request đang chạy.
- Bug mà PHP-FPM không có:
  - *Data race*: hai goroutine cùng truy cập một biến, ít nhất một bên ghi, không có đồng bộ.
  - Map bị ghi đồng thời làm crash process (module 1.1).
  - State của request này rò sang request khác.

*Connection DB*
- `*sql.DB` là một pool connection dùng chung trong process (module 2.5).
- PHP-FPM: mỗi worker giữ một connection riêng.

*Request context*
- `context.Context` (module 2.2) được truyền tường minh qua tham số đầu tiên của mỗi hàm. Nó mang
  deadline, tín hiệu huỷ và dữ liệu gắn với request.
- Laravel thì dùng request object và container theo request.

*Lỗi*
- Error value so với exception ([1.3](#13-error-panic-defer)).

*DI*
- Go nối dependency bằng tay ở `main`: gọi các constructor function như `NewService(repo, logger)`
  rồi truyền kết quả đi.
- Không có container như Laravel. Thư viện Wire và fx có tồn tại nhưng ít dùng.

*Deploy và kiểu dữ liệu*
- Deploy: một binary tĩnh. Không cần interpreter, PHP-FPM hay Nginx đứng trước (dù vẫn thường có
  load balancer).
- Không có OPcache, vì code đã được compile sẵn.
- Kiểu static, không có *type juggling* (tự đổi kiểu ngầm như `"1" == 1` của PHP), không có `==`
  lỏng. `==` với struct so từng field.

**Đọc**
- PHP: [FPM configuration](https://www.php.net/manual/en/install.fpm.configuration.php)
- Go: [net/http Server](https://pkg.go.dev/net/http#Server) (mỗi connection một goroutine)

- [ ] Giải thích được vì sao một map cache package-level chạy ổn khi viết tương đương bằng PHP-FPM, nhưng làm crash service Go
- [ ] So sánh được chi phí bộ nhớ cho 1000 request đồng thời giữa PHP-FPM và Go

#### 2.1 Interface sâu, generics, ngữ nghĩa vòng lặp

**Vì sao cần học:** Nil interface trap là câu hỏi vặn nổi tiếng nhất về Go. Generics và ngữ nghĩa
vòng lặp mới (1.22) đã đổi cách viết code Go vài năm gần đây, và người phỏng vấn dùng chúng để xem
bạn có theo kịp không.

**Học gì**

*Method set*
- *Method set* của một kiểu là tập method dùng để xét kiểu đó có thoả interface không:
  - Của `T`: chỉ gồm các method có value receiver.
  - Của `*T`: gồm cả method value receiver lẫn pointer receiver.
- Hệ quả: nếu `Save` có pointer receiver và `v` có kiểu `T`, thì `var i Saver = v` không compile.

*Nil interface trap*
- Một giá trị interface gồm hai phần: (type, value). Nó chỉ bằng `nil` khi **cả hai** đều nil.
- ⚠️ Bẫy:

  ```go
  func find() error {
      var e *MyErr = nil
      return e      // interface = (type *MyErr, value nil): type khác nil
  }

  err := find()
  fmt.Println(err != nil)   // true
  ```

*Nhúng interface vào struct*
- Struct nhúng một interface thì thoả interface đó ngay, dù chưa viết method nào.
- Gọi vào method chưa được implement thì panic, vì field interface bên trong là nil.
- Hay dùng trong test: nhúng interface, rồi chỉ viết đè đúng method cần giả.

*Generics*
- *Generics* (1.18): hàm hoặc kiểu có *type parameter*:

  ```go
  func Max[T cmp.Ordered](a, b T) T {
      if a > b {
          return a
      }
      return b
  }
  ```

- *Constraint* là một interface giới hạn những kiểu nào được dùng cho `T`:
  - `any`: mọi kiểu.
  - `comparable`: kiểu dùng được `==`.
  - `cmp.Ordered`: kiểu dùng được `<`, `>`.
  - `~int | ~string`: `int`, `string`, hoặc kiểu định nghĩa dựa trên chúng (như `type UserID int`).
    Dấu `~` nghĩa là "kể cả kiểu có kiểu gốc này".
- Package `slices`, `maps`, `cmp` (1.21) chứa sẵn các hàm generic như `slices.Contains`, `slices.Sort`.
- Các mốc mới:
  - 1.24: generic type alias.
  - 1.26: generic type được tự tham chiếu trong constraint của nó; `new(expr)` tạo con trỏ tới giá
    trị của một biểu thức.
  - 1.27: **generic method**, tức method có type parameter riêng.
    ⚠️ Generic method không dùng để thoả interface được.
- Khi nào không dùng generics: chỉ có một kiểu, hoặc interface thường đã đủ.
- Đối chiếu PHP: PHP không có generics, chỉ ghi `@template` trong docblock cho PHPStan.

*Biến vòng lặp*
- ⚠️ Trước 1.22, biến của vòng `for` là **một biến** dùng chung cho mọi vòng. Goroutine hoặc
  closure bắt biến đó thường đều thấy giá trị cuối cùng.
- Từ 1.22, mỗi vòng lặp có biến riêng.
- ⚠️ Áp dụng theo dòng `go` trong `go.mod`, không theo bản toolchain: module khai `go 1.21` vẫn
  theo ngữ nghĩa cũ, dù build bằng Go mới.

*Cú pháp range mới*
- `for i := range 10` (1.22): lặp `i` từ 0 tới 9.
- Range over function (1.23): `range` được trên một hàm có kiểu như `iter.Seq[T]`, để tự viết
  iterator. Gần giống generator dùng `yield` của PHP.

**Đọc**
- FAQ: [Why is my nil error value not equal to nil?](https://go.dev/doc/faq#nil_error)
- Spec: [Method sets](https://go.dev/ref/spec#Method_sets)
- Go blog: [When To Use Generics](https://go.dev/blog/when-generics), [Fixing For Loops in Go 1.22](https://go.dev/blog/loopvar-preview), [Range Over Function Types](https://go.dev/blog/range-functions), [Generic Methods](https://go.dev/blog/generic-methods)

#### 2.2 context, errgroup, pattern, goroutine leak

**Vì sao cần học:** Mọi service Go production đều truyền `context` qua gần như mọi hàm. Goroutine
leak là nguyên nhân phổ biến của "RAM tăng dần sau vài ngày". Câu hỏi thiết kế worker pool hay
pipeline hay xuất hiện ở vòng mid và senior.

**Học gì**

*context là gì*
- `context.Context` mang theo một request ba thứ: tín hiệu huỷ, deadline, và vài giá trị gắn với
  request đó.
- Tạo context con:
  - `ctx, cancel := context.WithCancel(parent)`: huỷ khi gọi `cancel()`.
  - `ctx, cancel := context.WithTimeout(parent, 2*time.Second)`: tự huỷ sau 2 giây.
  - ⚠️ Luôn `defer cancel()` ngay sau khi tạo, để giải phóng tài nguyên của context con.
- Huỷ lan từ cha xuống con: client ngắt request thì mọi query DB và lời gọi HTTP dùng context đó
  đều được báo dừng.
- Các hàm khác:
  - `WithCancelCause` (1.20): huỷ kèm lý do.
  - `WithoutCancel` (1.21): context con không bị huỷ theo cha.
  - `AfterFunc` (1.21): chạy một hàm khi context bị huỷ.
- Quy ước:
  - `ctx` là tham số đầu tiên của hàm.
  - Không lưu ctx trong struct.
  - Không truyền `nil` làm ctx.
- Đối chiếu PHP-FPM: gần nhất là timeout giết cả worker, không có cách báo "dừng lại" xuống từng
  query đang chạy.

*Bẫy của context*
- ⚠️ `WithValue` chỉ dành cho dữ liệu gắn với request (request ID, user đã xác thực). Dùng nó để
  truyền tham số hay dependency thì mất kiểm tra kiểu và che dependency.
  - Key phải là một kiểu unexported riêng, để không đụng key của package khác.
- ⚠️ Huỷ chỉ có tác dụng khi code **kiểm tra** `ctx.Done()`, hoặc truyền ctx cho hàm biết kiểm
  tra. Vòng lặp tính toán dài không kiểm tra thì vẫn chạy tiếp.
- ⚠️ Goroutine nền (ví dụ gửi email sau khi đã trả response) mà dùng ctx của request thì bị huỷ
  ngay khi request xong. Dùng `WithoutCancel`.

*errgroup*
- `errgroup.WithContext(ctx)` chạy một nhóm goroutine:
  - `Wait()` trả về lỗi đầu tiên.
  - Lỗi đầu tiên huỷ context chung, để các goroutine còn lại dừng.
- `SetLimit(n)`: tối đa `n` goroutine chạy cùng lúc.

*Các pattern*
- *Worker pool*: N goroutine cố định cùng đọc việc từ một channel.
- *Fan-out/fan-in*: chia việc cho nhiều goroutine (fan-out), rồi gom kết quả về một channel (fan-in).
- *Pipeline*: chuỗi các stage nối nhau bằng channel, stage trước xuất dữ liệu cho stage sau.
  - Mọi stage phải thoát được khi ctx bị huỷ.
- *Semaphore* bằng channel: `sem := make(chan struct{}, n)`. Gửi vào trước khi làm, nhận ra khi
  xong, nên tối đa `n` việc chạy cùng lúc.

*Goroutine leak*
- *Goroutine leak*: goroutine bị block mãi, không bao giờ kết thúc, giữ RAM và mọi thứ nó tham chiếu.
- Nguyên nhân hay gặp:
  - Gửi vào channel mà bên nhận đã bỏ đi (ví dụ đã timeout).
  - Chờ nhận từ một channel không bao giờ được đóng.
  - Gọi HTTP không có timeout.
- Chuỗi sự cố kinh điển:
  1. Hàm tạo một unbuffered channel, chạy goroutine gọi API rồi gửi kết quả vào channel.
  2. Hàm `select` giữa channel đó và timeout 1 giây.
  3. Timeout đến trước, hàm return.
  4. API trả về sau, goroutine gửi vào channel nhưng không còn ai nhận, nên kẹt mãi.
- Sửa: dùng channel buffer 1 (gửi được mà không cần người nhận), hoặc `select` cả trên `ctx.Done()`
  khi gửi.

*time.After trong vòng lặp*
- `time.After(d)` tạo một timer mới mỗi lần gọi.
- Từ Go 1.23, timer không còn ai tham chiếu được GC thu hồi ngay, kể cả khi chưa hết hạn.
- ⚠️ Hành vi mới chỉ áp dụng khi `go.mod` khai `go >= 1.23`. Hành vi cũ giữ lại được qua GODEBUG
  `asynctimerchan` (*GODEBUG* là cài đặt để bật lại hành vi cũ của runtime).
- Go 1.27 bỏ hẳn GODEBUG `asynctimerchan`, nên build bằng toolchain 1.27 luôn theo hành vi mới.

*Phát hiện leak*
- `runtime.NumGoroutine()` tăng dần theo thời gian.
- pprof goroutine: xem goroutine đang kẹt ở dòng nào.
- `goleak`: kiểm tra trong test.
- Profile `goroutineleak` (module 3.3).

**Đọc**
- Go blog: [Go Concurrency Patterns: Context](https://go.dev/blog/context), [Pipelines and cancellation](https://go.dev/blog/pipelines)
- Package [context](https://pkg.go.dev/context), [errgroup](https://pkg.go.dev/golang.org/x/sync/errgroup)
- Release notes 1.23: [Timer changes](https://go.dev/doc/go1.23#timer-changes)

**Nắm chắc khi**
- [ ] Viết được worker pool gọi URL, tối đa 5 đồng thời, dừng khi lỗi đầu tiên hoặc sau 10 giây (bài tập 2)
- [ ] Viết được hàm leak goroutine kinh điển (timeout + unbuffered channel) rồi sửa (bài tập 5)
- [ ] Thiết kế được pipeline 3 stage huỷ được giữa chừng mà không leak

#### 2.3 Memory model, atomic, race

**Vì sao cần học:** Go cho nhiều goroutine cùng chạm vào một vùng nhớ, và compiler cùng CPU được
phép đổi thứ tự lệnh. Không nắm happens-before thì không trả lời được "đoạn code này có race
không", câu hỏi phân biệt mid với junior.

**Học gì**

*Happens-before*
- CPU và compiler được phép đổi thứ tự lệnh, và mỗi core có cache riêng. Vì vậy một goroutine ghi
  biến, goroutine khác chưa chắc thấy giá trị mới.
- *Happens-before*: A happens-before B thì B chắc chắn thấy mọi thứ A đã ghi. Không có quan hệ này
  thì không có gì được đảm bảo.
- Các cặp tạo happens-before:
  - Gửi vào channel → lần nhận tương ứng hoàn tất.
  - `Unlock` → lần `Lock` sau đó trên cùng mutex.
  - Hàm chạy trong `Once.Do` → mọi lời gọi `Do` trả về.
  - Ghi atomic → lần đọc atomic thấy giá trị đó.
- ⚠️ Không có "race lành tính" trong Go memory model. Race là bug, kể cả khi "chỉ là một cờ bool".

*Atomic*
- `sync/atomic` có `atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]` (1.19). Hợp cho counter và cờ.
- Nhiều biến phải nhất quán với nhau (ví dụ `count` và `sum` luôn đi cùng) thì dùng mutex, vì
  atomic chỉ đảm bảo cho từng biến riêng lẻ.

*Các công cụ khác trong sync*
- `RWMutex` chỉ có lợi khi đọc chiếm đa số và đoạn đọc đủ dài.
- `sync.Pool`: kho object tạm để tái dùng (ví dụ buffer), giảm allocation.
  - ⚠️ Object trong pool có thể bị xoá ở bất kỳ lần GC nào.
  - Reset object trước khi `Put` vào pool, nếu không lần `Get` sau thấy dữ liệu cũ.
  - Không dùng làm connection pool.
- `sync.Map`: map an toàn đồng thời, hợp hai trường hợp:
  - Key được ghi một lần rồi đọc nhiều.
  - Các goroutine làm việc trên những tập key rời nhau.

*Race detector*
- `go test -race`: compiler chèn thêm code theo dõi mọi truy cập bộ nhớ.
- Chỉ bắt race **thực sự xảy ra** trong lần chạy đó. Đường code không được chạy tới thì không bắt được.
- Chậm và tốn RAM gấp nhiều lần, nên chạy trong test và CI.

**Đọc**
- [The Go Memory Model](https://go.dev/ref/mem) (phần *Advice* ở đầu và *Synchronization*)
- [Data Race Detector](https://go.dev/doc/articles/race_detector)
- Package [sync/atomic](https://pkg.go.dev/sync/atomic)

#### 2.4 net/http production

**Vì sao cần học:** Service Go thường dùng thẳng `net/http` của thư viện chuẩn, không cần framework
như Laravel. Nhưng giá trị mặc định của nó không an toàn cho production (không có timeout), và đây
là nguồn câu hỏi "chỉ ra lỗi trong đoạn code này".

**Học gì**

*Handler, middleware, routing*
- `http.Handler` là interface có một method `ServeHTTP(w, r)`. `http.HandlerFunc` biến một hàm
  thường thành Handler.
- *Middleware* có dạng `func(next http.Handler) http.Handler`: bọc handler, làm gì đó trước và sau
  khi gọi `next.ServeHTTP`. Giống `handle($request, $next)` của middleware Laravel.
- `ServeMux` từ 1.22 hỗ trợ method và tham số trong path: đăng ký `"GET /users/{id}"`, lấy tham số
  bằng `r.PathValue("id")`.
- ⚠️ Header phải ghi trước body. Sau khi đã `Write` body, sửa header không còn tác dụng. Giống lỗi
  "headers already sent" của PHP.

*Server và timeout*
- ⚠️ `http.Server` zero value **không có timeout** nào. Client cố tình gửi từng byte thật chậm
  (tấn công *slowloris*) giữ connection và goroutine mãi.
- Bốn timeout cần đặt:
  - `ReadHeaderTimeout`: đọc xong header.
  - `ReadTimeout`: đọc xong cả request, gồm body.
  - `WriteTimeout`: ghi xong response.
  - `IdleTimeout`: giữ connection keep-alive đang rảnh bao lâu.
- Giới hạn kích thước body bằng `http.MaxBytesReader`.

*Client gọi API ngoài*
- ⚠️ `http.Get` và `http.DefaultClient` không có timeout. Đối tác treo thì goroutine và connection
  treo theo.
- Tạo `&http.Client{Timeout: ...}` **một lần** và dùng lại (client giữ pool connection bên trong),
  kết hợp với ctx theo request.
- ⚠️ Luôn `defer resp.Body.Close()` và đọc hết body, để connection được trả về pool và dùng lại.
- ⚠️ Response 4xx/5xx **không** trả về `err`. `err` chỉ khác nil khi lỗi ở tầng mạng, còn status
  phải tự kiểm tra. Giống HTTP client của Laravel, không tự ném lỗi với 4xx/5xx.
- `Transport.MaxIdleConnsPerHost` mặc định là 2: chỉ giữ lại 2 connection rảnh cho mỗi host. Gọi
  nhiều tới cùng một host thì phải mở connection mới liên tục, nên tăng giá trị này.

*Graceful shutdown*
- Nghĩa là tắt app mà không cắt ngang request đang chạy. Các bước:

1. Bắt tín hiệu `SIGTERM` bằng `signal.NotifyContext`.
2. Gọi `srv.Shutdown(ctx)`: ngừng nhận connection mới, chờ request đang chạy xong.
3. Dừng các worker nền.
4. Flush log.
5. Đóng DB.

- Trên Kubernetes:
  - Cho readiness probe fail trước, để load balancer ngừng gửi request mới.
  - `terminationGracePeriodSeconds` phải lớn hơn timeout shutdown, nếu không pod bị giết giữa chừng.

**Đọc**
- Package [net/http](https://pkg.go.dev/net/http) (đọc type `Server`, `Client`, `Transport`)
- Go blog: [Routing Enhancements for Go 1.22](https://go.dev/blog/routing-enhancements)
- Cloudflare: [The complete guide to Go net/http timeouts](https://blog.cloudflare.com/the-complete-guide-to-golang-net-http-timeouts/) (có sơ đồ timeout nào tính từ lúc nào)

**Nắm chắc khi**
- [ ] Viết được server có middleware log thời gian, đủ 4 timeout và graceful shutdown khi nhận `SIGTERM` (bài tập 4)
- [ ] Kể được 4 lỗi trong một đoạn code gọi API đối tác bằng `http.Get`

#### 2.5 database/sql và JSON

**Vì sao cần học:** Gần như service Go nào cũng dùng hai package này. Pool DB cạn vì quên đóng
`rows`, và ID lớn bị sai khi decode JSON, là hai lỗi production kinh điển.

**Học gì**

*sql.DB là pool*
- `*sql.DB` không phải một connection mà là một **pool** connection, an toàn khi nhiều goroutine
  dùng chung. Tạo một lần lúc khởi động và dùng suốt đời app.
- `sql.Open` chưa kết nối gì cả. Gọi `PingContext` để chắc DB đã sẵn sàng.
- Cấu hình pool:
  - `SetMaxOpenConns`: số connection tối đa. ⚠️ Mặc định 0, nghĩa là **không giới hạn**.
  - `SetMaxIdleConns`: số connection rảnh được giữ lại, mặc định 2.
  - `SetConnMaxLifetime`, `SetConnMaxIdleTime`: đóng connection đã quá già hoặc rảnh quá lâu.
- Tổng max open × số instance phải nhỏ hơn giới hạn connection của DB.

*Query và rows*
- ⚠️ Quên `rows.Close()` thì connection không về pool. Pool cạn dần, và request sau treo chờ
  connection.
- Sau vòng lặp `rows.Next()` phải kiểm tra `rows.Err()`, vì lỗi xảy ra giữa chừng nằm ở đó.
- Không có dòng nào thì `QueryRow(...).Scan(...)` trả `sql.ErrNoRows`.
- Cột có thể NULL: dùng `sql.Null[T]` (1.22) hoặc con trỏ.
- Luôn dùng biến thể `...Context` (`QueryContext`, `ExecContext`) để query bị huỷ theo request.

*Transaction*
- `db.BeginTx` trả về `tx`, giữ riêng một connection tới khi commit hoặc rollback.
- ⚠️ Trong transaction phải dùng `tx.Query`, không dùng `db.Query`.
  - `db.Query` lấy một connection khác, nên chạy **ngoài** transaction.
  - Pool nhỏ thì có thể deadlock: tx giữ connection cuối cùng, còn `db.Query` chờ connection mãi.
- `defer tx.Rollback()` ngay sau khi mở là an toàn: sau `Commit` thì `Rollback` không làm gì.

*Thư viện*
- `sqlx`: tiện ích scan kết quả vào struct.
- `sqlc`: sinh code Go từ file SQL.
- `pgx`: driver Postgres.
- GORM: ORM, gần với Eloquent nhất.

*JSON*
- Chỉ field exported (viết hoa chữ đầu) mới được encode và decode.
- *Tag* điều khiển tên và hành vi, ví dụ `json:"user_id,omitempty"`:
  - `omitempty`: bỏ field khi rỗng.
  - `-`: không bao giờ encode field này.
  - `string`: encode số dưới dạng chuỗi.
- ⚠️ `omitempty` không bỏ struct có zero value, ví dụ `time.Time{}` vẫn được encode. Go 1.24 có
  `omitzero` để bỏ.
- ⚠️ Decode số vào `any` sẽ ra `float64`, mất chính xác với ID lớn. Dùng `Decoder.UseNumber()`
  hoặc decode vào struct có kiểu.
- `DisallowUnknownFields()`: báo lỗi khi JSON có field lạ, dùng cho API strict.
- `encoding/json/v2` và `jsontext`:
  - Thử nghiệm ở 1.25, chính thức ở 1.27.
  - Mặc định chặt hơn: từ chối UTF-8 sai và key trùng.
  - `encoding/json` v1 giữ API cũ nhưng chạy trên implementation mới.

**Đọc**
- [Accessing relational databases](https://go.dev/doc/database/), [Managing connections](https://go.dev/doc/database/manage-connections)
- Package [database/sql](https://pkg.go.dev/database/sql), [encoding/json](https://pkg.go.dev/encoding/json), [encoding/json/v2](https://pkg.go.dev/encoding/json/v2)
- Go blog: [A new experimental Go API for JSON](https://go.dev/blog/jsonv2-exp)

**Nắm chắc khi**
- [ ] Đọc `db.Stats()` (InUse, WaitCount) và chỉ ra được pool đang cạn vì đâu
- [ ] Chỉ ra được 3 lỗi trong một hàm transaction dùng lẫn `db` và `tx`, return sớm quên close rows

#### 2.6 Testing nâng cao

**Vì sao cần học:** Go có sẵn benchmark, fuzzing và công cụ test code đồng thời ngay trong
`go test`. Senior Go được kỳ vọng đo trước khi tối ưu, và test được code có timeout mà không làm
test chậm.

**Học gì**

*Benchmark*
- Hàm benchmark có dạng `func BenchmarkX(b *testing.B)`, chạy bằng `go test -bench=.`.
- Từ 1.24 viết vòng đo bằng `b.Loop()`, thay cho `for i := 0; i < b.N; i++`:

  ```go
  func BenchmarkBuild(b *testing.B) {
      data := setup()   // phần setup không bị tính vào thời gian đo
      for b.Loop() {
          build(data)
      }
  }
  ```

  - `b.Loop` tự loại phần setup khỏi thời gian đo.
  - Nó cũng chống compiler xoá code có kết quả không ai dùng (*dead-code elimination*), thứ làm số
    đo đẹp giả.
- `-benchmem` hiện thêm số allocation. So sánh hai phiên bản bằng công cụ `benchstat`.
- ⚠️ Benchmark trên laptop dao động nhiều, nên chạy nhiều lần.

*Fuzzing*
- *Fuzzing* (1.18): Go tự sinh input ngẫu nhiên để tìm input làm hàm panic hoặc cho kết quả sai.
- Hàm có dạng `func FuzzX(f *testing.F)`. `f.Add(...)` thêm input mẫu ban đầu (*seed corpus*).
  Chạy bằng `go test -fuzz=FuzzX`.
- Input gây lỗi được lưu vào `testdata/fuzz`.

*testing/synctest*
- `testing/synctest` (GA 1.25): chạy code trong một "bubble" có đồng hồ ảo.
  - Trong bubble, thời gian chỉ nhảy tới khi mọi goroutine đều đang chờ, nên chờ 30 giây trôi qua
    ngay lập tức.
  - `synctest.Test(t, ...)` tạo bubble.
  - `synctest.Wait()` chờ tới khi mọi goroutine trong bubble đều bị block.
- Dùng để test timeout, retry, ticker mà không cần `time.Sleep` thật.
- Go 1.27 thêm `synctest.Sleep`.

*Race, leak, coverage*
- Chạy `go test -race ./...` trong CI.
- `goleak`: kiểm tra còn goroutine nào sót lại sau test không.
- Coverage: `go test -cover`. `go build -cover` build ra binary có đo coverage, dùng cho integration test.

*Integration test*
- Test với DB thật (Docker hoặc Testcontainers), tách khỏi unit test bằng build tag hoặc
  `testing.Short()`.
- Nguyên lý test chung: [20-testing-quality.md](20-testing-quality.md).

**Đọc**
- Package [testing](https://pkg.go.dev/testing) (mục [Benchmarks](https://pkg.go.dev/testing#hdr-Benchmarks), [Fuzzing](https://pkg.go.dev/testing#hdr-Fuzzing))
- Go blog: [More predictable benchmarking with testing.B.Loop](https://go.dev/blog/testing-b-loop), [Testing concurrent code with testing/synctest](https://go.dev/blog/synctest)
- [Go Fuzzing](https://go.dev/doc/security/fuzz/), [Tutorial: Getting started with fuzzing](https://go.dev/doc/tutorial/fuzz)
- Package [testing/synctest](https://pkg.go.dev/testing/synctest), [goleak](https://github.com/uber-go/goleak), [Coverage for integration tests](https://go.dev/doc/build-cover)

**Nắm chắc khi**
- [ ] Viết được benchmark so sánh `strings.Builder` với `+=` bằng `b.Loop`, đọc được `ns/op` và `allocs/op`

#### 2.7 Logging với log/slog

**Vì sao cần học:** Log có cấu trúc là điều kiện để tìm được log trên production. Go có sẵn
`log/slog` từ 1.21, không cần thư viện ngoài như Monolog. Hay được hỏi cùng chuyện gắn request ID
vào mọi dòng log.

**Học gì**

*slog cơ bản*
- *Structured logging*: mỗi dòng log là một tập key/value thay vì chuỗi tự do, để hệ thống log lọc
  được theo field.
- `slog.Info("msg", "user_id", id)`: message kèm các cặp key/value.
- `slog.With(...)` tạo logger gắn sẵn field cố định cho mọi dòng sau.

*Handler*
- *Handler* quyết định định dạng và nơi ghi log, giống handler của Monolog:
  - `TextHandler`: dạng `key=value`, dễ đọc khi dev.
  - `JSONHandler`: dạng JSON, cho production.
  - Tự viết custom handler.
  - `NewMultiHandler` (1.26): ghi ra nhiều đích cùng lúc.
- Level động: `slog.LevelVar` đổi level lúc đang chạy mà không restart.
- `LogValuer`: kiểu tự quyết định mình hiện ra thế nào trong log, dùng để che dữ liệu nhạy cảm
  (password, token).

*Gắn request ID và trace ID*
1. Middleware đọc hoặc sinh request ID, gắn vào `ctx`.
2. Code gọi `InfoContext(ctx, ...)` thay vì `Info(...)`.
3. Handler đọc request ID từ ctx và thêm vào mỗi dòng log.

- Đối chiếu PHP: Monolog kết hợp context và processor của Laravel.

*Bẫy*
- ⚠️ Truyền số tham số lẻ (thiếu value cho một key) sinh ra key `!BADKEY` trong log.
- Ở code nóng, dùng `slog.Attr` (`slog.Int`, `slog.String`) để tránh allocation.
- ⚠️ Log một lần ở chỗ xử lý lỗi, không log ở mọi tầng (module 1.3).
- Observability chung: [18-reliability-observability.md](18-reliability-observability.md).

**Đọc**
- Go blog: [Structured Logging with slog](https://go.dev/blog/slog)
- Package [log/slog](https://pkg.go.dev/log/slog)

**Nắm chắc khi**
- [ ] Viết được middleware gắn request ID vào mọi dòng log của request đó, output JSON
- [ ] Che được field `password` trong log bằng `LogValuer`

#### 2.8 Project layout và module

**Vì sao cần học:** Go không có cấu trúc thư mục cố định như Laravel, nên câu "bạn tổ chức project
thế nào" rất hay gặp. Go modules cũng giải dependency theo cách khác hẳn Composer.

**Học gì**

*Cấu trúc thư mục*
- `cmd/<app>/main.go`: mỗi binary một thư mục.
- `pkg/`: một quy ước gây tranh cãi, không bắt buộc.
- `internal/`: package nằm trong `a/b/internal/x` chỉ import được từ code nằm trong cây thư mục gốc
  tại `a/b` (thư mục cha của `internal`).
  - ⚠️ Không phải "cả module import được".
- ⚠️ Repo "golang-standards/project-layout" **không** phải chuẩn chính thức.
- Chia package theo domain (`order`, `payment`), tránh package kiểu `utils`/`common` gom đủ thứ.
- ⚠️ Import vòng (package A import B, B lại import A) là lỗi compile.

*go.mod và go.sum*
- `go.mod`, vai trò như `composer.json`: khai module path, dòng `go`, và các dependency.
- `go.sum`: checksum của từng dependency, để phát hiện code bị thay đổi. Commit cả hai file.
- Dòng `go` quyết định ngữ nghĩa ngôn ngữ (vòng lặp ở module 2.1, timer ở module 2.2) và các giá
  trị GODEBUG mặc định.

*Minimal version selection*
- *Minimal version selection* (MVS): với mỗi dependency, Go chọn phiên bản **thấp nhất** thoả mọi
  yêu cầu trong cây dependency.
  - Ví dụ: A cần `x >= 1.2`, B cần `x >= 1.4` thì chọn 1.4, dù đã có bản 1.9.
- Vì kết quả chỉ phụ thuộc vào các file `go.mod`, build tái lập được mà không cần lock file.
- Major version từ 2 trở lên đổi import path, ví dụ thêm hậu tố `/v2`.

*Lệnh và directive*
- `go mod tidy`: thêm dependency còn thiếu, bỏ dependency thừa.
- `replace`: trỏ một dependency sang bản local hoặc bản fork.
- `GOPROXY`: nơi tải module. `GOPRIVATE`: module nội bộ, không đi qua proxy công khai.
- `go mod vendor`: copy dependency vào thư mục `vendor/`.
- Directive trong `go.mod`:
  - `toolchain` (1.21): chọn bản Go dùng để build.
  - `tool` (1.24): khai công cụ dev.
  - `ignore` (1.25): bỏ qua thư mục.
- `go fix` (1.26) là nơi chứa các "modernizer" tự nâng code lên idiom mới.

**Đọc**
- [Organizing a Go module](https://go.dev/doc/modules/layout)
- [cmd/go: Internal packages](https://pkg.go.dev/cmd/go#hdr-Internal_packages)
- [Go Modules Reference](https://go.dev/ref/mod) (mục [MVS](https://go.dev/ref/mod#minimal-version-selection), [Major version suffixes](https://go.dev/ref/mod#major-version-suffixes)); [Go Toolchains](https://go.dev/doc/toolchain)
- Russ Cox: [Minimal Version Selection](https://research.swtch.com/vgo-mvs)

**Nắm chắc khi**
- [ ] Cho một cây thư mục có `internal/`, nói đúng package nào import được
- [ ] So sánh được MVS với cách Composer giải dependency và vai trò của `composer.lock`

#### 3.1 Scheduler G-M-P

**Vì sao cần học:** "Vì sao 100.000 goroutine không cần 100.000 thread" là câu senior Go kinh điển.
Hiểu scheduler giải thích vì sao Go xử lý I/O tốt, và giúp đọc được trace ở module 3.3.

**Học gì**

*Ba thành phần G, M, P*
- G: goroutine.
- M (*machine*): một OS thread thật.
- P (*processor*): một bộ xử lý logic. Số P bằng `GOMAXPROCS` (module 3.4).
- M phải giữ một P thì mới chạy được G.
- Kiểu nhiều goroutine chạy trên ít thread này gọi là mô hình *M:N*.

*Phân việc*
- Mỗi P có một hàng đợi riêng (*local run queue*) chứa các G sẵn sàng chạy.
- P hết việc thì:
  1. Lấy G từ global queue.
  2. Không có thì *steal*: lấy một nửa hàng đợi của một P khác (*work stealing*).

*Khi goroutine bị chặn*
- Syscall blocking, ví dụ đọc file:
  1. M đang chạy G bị kẹt trong kernel.
  2. P được tách khỏi M đó và trao cho một M khác, để các G còn lại vẫn chạy.
  3. Syscall xong, G quay lại hàng đợi.
- I/O mạng đi qua *netpoller* (dùng epoll trên Linux, kqueue trên macOS):
  - G đang chờ mạng được *park* (cất sang một bên), không chiếm thread.
  - Dữ liệu tới thì G được đưa lại vào hàng đợi.

*Preemption*
- *Preemption*: scheduler ngắt một goroutine đang chạy để goroutine khác được chạy.
- Từ 1.14 có preemption bất đồng bộ: vòng lặp chặt không gọi hàm nào vẫn bị ngắt được.

*Đối chiếu*
- Virtual thread của Java ([06-java-spring.md](06-java-spring.md)) cùng ý tưởng M:N.
- PHP-FPM là 1 request : 1 process. Worker chờ I/O thì cả process đứng chờ.

**Đọc**
- Ardan Labs: [Scheduling In Go, Part I (OS)](https://www.ardanlabs.com/blog/2018/08/scheduling-in-go-part1.html), [Part II (Go Scheduler)](https://www.ardanlabs.com/blog/2018/08/scheduling-in-go-part2.html)
- 🔴 Dmitry Vyukov: [Scalable Go Scheduler Design Doc](https://golang.org/s/go11sched)

#### 3.2 Bộ nhớ: escape analysis và GC

**Vì sao cần học:** Service Go tốn RAM hoặc CPU cao vì GC thường bắt nguồn từ allocation. Câu hỏi
về `GOGC` và `GOMEMLIMIT` hay đi kèm chủ đề chạy trên Kubernetes. PHP-FPM ít cần biết chuyện này vì
worker chết là trả hết RAM.

**Học gì**

*Stack, heap và escape analysis*
- Biến trên *stack* được giải phóng miễn phí khi hàm return. Biến trên *heap* phải chờ GC dọn.
- *Escape analysis*: compiler tự quyết định biến nằm trên stack hay heap. Biến "thoát" (*escape*)
  khỏi hàm thì phải lên heap.
- Trả con trỏ tới biến local là an toàn, vì compiler tự đưa biến đó lên heap.
- Xem compiler quyết định gì: `go build -gcflags=-m`.
- Nguyên nhân escape hay gặp:
  - Trả con trỏ ra ngoài hàm.
  - Gán vào interface.
  - Closure bắt biến.
  - Kích thước không biết lúc compile.
- Go 1.26 đặt backing array của slice lên stack trong nhiều trường hợp hơn.

*GC của Go*
- *Concurrent mark-sweep*: đánh dấu (*mark*) các object còn sống song song với chương trình, rồi
  quét dọn (*sweep*) phần còn lại.
- Không chia thế hệ như JVM, và không *compact* (không dồn object lại cho liền nhau).
- Trong pha mark có *write barrier*: mỗi lần ghi con trỏ, chương trình làm thêm chút việc để GC
  không bỏ sót object.
- **Green Tea GC**:
  - Thử nghiệm ở 1.25 (`GOEXPERIMENT=greenteagc`), **mặc định từ 1.26**.
  - Quét theo span/page (khối bộ nhớ chứa nhiều object) thay vì từng object, nên đọc bộ nhớ liền
    mạch hơn (*locality* tốt hơn).
  - Giảm 10–40% chi phí GC với chương trình nặng GC.

*GOGC và GOMEMLIMIT*
- *Live heap*: phần heap còn sống sau một lần GC.
- `GOGC` (mặc định 100): GC chạy khi heap tăng thêm 100% so với live heap sau lần trước. Ví dụ live
  heap 200 MB thì lần GC sau ở khoảng 400 MB.
- `GOMEMLIMIT` (1.19): giới hạn mềm cho tổng bộ nhớ. Gần chạm giới hạn thì GC chạy dày hơn.
- ⚠️ Live heap sát limit: GC chạy liên tục mà không thu được bao nhiêu (*thrash*), CPU cao.

*Giảm áp lực GC*
- Ít allocation: cấp trước kích thước slice, tái dùng buffer, dùng `sync.Pool`.
- Ít con trỏ, vì GC phải lần theo từng con trỏ.
- Struct alignment/padding: compiler chèn byte trống giữa các field để chúng thẳng hàng. Sắp field
  từ lớn tới nhỏ để giảm phần trống.
- Package `weak` (con trỏ yếu, không giữ object sống) và `runtime.AddCleanup` (1.24) thay cho
  `SetFinalizer`.

**Đọc**
- [A Guide to the Go Garbage Collector](https://go.dev/doc/gc-guide) (mục [GOGC](https://go.dev/doc/gc-guide#GOGC), [Memory limit](https://go.dev/doc/gc-guide#Memory_limit), [Eliminating heap allocations](https://go.dev/doc/gc-guide#Eliminating_heap_allocations)). Đọc phần có hình tương tác
- Go blog: [The Green Tea Garbage Collector](https://go.dev/blog/greenteagc)
- Release notes 1.26: [Runtime](https://go.dev/doc/go1.26#runtime)

**Nắm chắc khi**
- [ ] Đọc được output `-gcflags=-m` và giải thích vì sao một biến escape
- [ ] Nói được `GOGC=200` và `GOMEMLIMIT=900MiB` mỗi cái đổi gì, và khi nào kết hợp cả hai

#### 3.3 Profiling và chẩn đoán

**Vì sao cần học:** "Service chậm hoặc RAM tăng, bạn làm gì" là câu senior rất phổ biến. Go có sẵn
pprof và trace, nên người phỏng vấn mong bạn đo bằng công cụ chứ không đoán.

**Học gì**

*pprof*
- `import _ "net/http/pprof"` mở các endpoint `/debug/pprof/`.
  - ⚠️ Không expose ra internet.
- Các loại profile:

  | Profile | Cho biết | Dùng khi |
  |---|---|---|
  | CPU | Hàm nào ăn CPU | CPU cao |
  | `heap`, chế độ `inuse_space` | Bộ nhớ **đang** bị giữ, theo chỗ cấp | Tìm leak |
  | `heap`, chế độ `alloc_space` | Tổng bộ nhớ đã cấp, kể cả phần đã được thu hồi | Tìm chỗ allocate nhiều |
  | `goroutine` | Mỗi goroutine đang đứng ở dòng nào | Leak goroutine, treo |
  | `block`, `mutex` | Chờ channel hay lock ở đâu | Chậm mà CPU thấp |

  - `block` và `mutex` phải bật trước bằng `SetBlockProfileRate` và `SetMutexProfileFraction`.
- Xem profile: `go tool pprof -http=:8080 <url|file>` mở giao diện web có *flame graph*
  (biểu đồ cho thấy hàm nào chiếm bao nhiêu thời gian), bảng top, và list (xem theo từng dòng code).

*trace*
- `go tool trace`: xem scheduler, GC, goroutine theo trục thời gian.
- Flight recorder (`runtime/trace.FlightRecorder`, 1.25): giữ vài giây trace gần nhất trong RAM,
  và chụp lại khi có sự kiện lạ.
- Profile `goroutineleak`:
  - Thử nghiệm ở 1.26, chính thức ở 1.27.
  - Dùng GC để tìm goroutine bị block vĩnh viễn trên một primitive (channel, mutex) mà không goroutine
    nào khác còn với tới được.

*PGO*
- *PGO* (profile-guided optimization): build với CPU profile lấy từ production (file `default.pgo`),
  để compiler tối ưu mạnh hơn các đường code nóng.

*Quy trình chẩn đoán*
1. Thấy metric bất thường.
2. Lấy đúng loại profile.
3. Đặt giả thuyết.
4. Sửa.
5. Đo lại.

**Đọc**
- [Diagnostics](https://go.dev/doc/diagnostics) (mục [Profiling](https://go.dev/doc/diagnostics#profiling))
- Package [net/http/pprof](https://pkg.go.dev/net/http/pprof), [runtime/pprof](https://pkg.go.dev/runtime/pprof)
- Go blog: [Profiling Go Programs](https://go.dev/blog/pprof), [Flight Recorder in Go 1.25](https://go.dev/blog/flight-recorder)
- [Profile-guided optimization](https://go.dev/doc/pgo)

**Nắm chắc khi**
- [ ] Từ goroutine profile của một service leak, chỉ ra được dòng code đang kẹt
- [ ] Phân biệt được khi nào nhìn `inuse_space` và khi nào nhìn `alloc_space`

#### 3.4 Go trong container

**Vì sao cần học:** Chuyển service Go lên Kubernetes rồi thấy p99 tăng là sự cố hay gặp và là câu
hỏi senior phổ biến. Nguyên nhân nằm ở cách Go đếm CPU, và ở việc Go không tự biết memory limit.

**Học gì**

*CPU và GOMAXPROCS*
- `GOMAXPROCS` là số P (module 3.1), tức số goroutine chạy song song thật sự.
- *CFS throttle*: container có CPU limit 2 thì trong mỗi chu kỳ ngắn chỉ được dùng lượng CPU tương
  đương 2 core. Dùng hết sớm thì mọi thread bị dừng tới chu kỳ sau.
- Trước Go 1.25:
  - `GOMAXPROCS` bằng số CPU của node, không đọc CPU limit của *cgroup* (giới hạn tài nguyên của
    container).
  - Pod limit 2 CPU trên node 64 core chạy quá nhiều thread song song, dùng hết quota rất nhanh, bị
    throttle, nên p99 tăng.
  - Cách xử lý cũ: thư viện `go.uber.org/automaxprocs`.
- Go 1.25+:
  - `GOMAXPROCS` mặc định theo CPU limit của cgroup (nếu thấp hơn số CPU), và tự cập nhật khi limit đổi.
  - Tắt bằng biến môi trường `GOMAXPROCS`, hoặc GODEBUG `containermaxprocs=0`, `updatemaxprocs=0`.
  - ⚠️ Chỉ áp dụng khi dòng `go` trong `go.mod` ≥ 1.25.
  - ⚠️ CPU request (khi không có limit) không ảnh hưởng.

*Memory*
- Go không tự đọc memory limit của container.
- Đặt `GOMEMLIMIT` khoảng 90% limit container.

*Image*
- Binary tĩnh nên image rất nhỏ (distroless, scratch).
- ⚠️ Image tối giản không có sẵn gì: nhớ đưa vào CA cert (để gọi HTTPS) và timezone data.
- Chi tiết Kubernetes: [19-devops-cloud.md](19-devops-cloud.md).

**Đọc**
- Go blog: [Container-aware GOMAXPROCS](https://go.dev/blog/container-aware-gomaxprocs)
- Release notes: [Go 1.25](https://go.dev/doc/go1.25)
- [automaxprocs](https://github.com/uber-go/automaxprocs) (bối cảnh cho bản Go cũ)

**Nắm chắc khi**
- [ ] Giải thích được vì sao p99 tăng gấp đôi khi chuyển từ VM sang pod limit 2 CPU trên Go 1.24, và vì sao Go 1.25+ thường không còn gặp
- [ ] Cấu hình được `GOMEMLIMIT` cho pod limit 1 GiB và nói lý do để khoảng trống

## Phần 2: Câu hỏi thường gặp (bonus)

Cách dùng: tự trả lời thành tiếng trước, sau đó mới đối chiếu với hướng trả lời. Câu nào bị
đơ thì quay lại module ghi trong ngoặc.

### 🟢 Junior

**1. Ghi vào nil map thì sao? Đọc thì sao?** (1.1)
- Ý phải có: đọc trả zero value, ghi thì panic
- Điểm cộng: ghi đồng thời là fatal error không recover được

**2. `len("tiếng Việt")` trả về bao nhiêu, vì sao?** (1.1)
- Ý phải có: đếm byte UTF-8, không đếm ký tự; dùng `utf8.RuneCountInString`
- Điểm cộng: `range` duyệt theo rune; cắt chuỗi giữa ký tự

**3. Error của Go khác exception của PHP/Java thế nào?** (1.3, 1.6)
- Ý phải có: giá trị trả về, xử lý tường minh; wrap bằng `%w`; `panic` chỉ cho lỗi lập trình
- Điểm cộng: được và mất của mỗi mô hình; map lỗi sang HTTP ở biên
- Red flag: dùng `panic`/`recover` như try/catch

**4. Viết test table-driven thế nào? Vì sao dùng `t.Run`?** (1.5)
- Ý phải có: slice case, lặp, subtest; chạy riêng được bằng `-run`, báo lỗi theo tên case
- Điểm cộng: `t.Parallel()`; `httptest` cho handler

**5. Service Go xử lý request khác PHP-FPM thế nào?** (1.6)
- Ý phải có: một process, mỗi request một goroutine, state dùng chung; FPM share-nothing
- Điểm cộng: hệ quả race và map; pool DB trong process

### 🟡 Mid

**6. Vì sao một hàm trả `*MyErr` bằng nil lại khiến `err != nil`?** (2.1)
- Ý phải có: interface là cặp (type, value); type khác nil nên interface khác nil
- Điểm cộng: 2 cách sửa; kiểm tra bằng `errors.As`

**7. Vòng `for` tạo goroutine in biến vòng lặp: trước và sau Go 1.22 in ra gì?** (2.1)
- Ý phải có: trước 1.22 dùng chung biến nên thường in giá trị cuối; từ 1.22 mỗi vòng một biến
- Điểm cộng: phụ thuộc dòng `go` trong `go.mod`, không phụ thuộc bản toolchain

**8. Đọc từ channel đã đóng, gửi vào channel đã đóng, đóng nil channel thì sao?** (1.4)
- Ý phải có: zero value + `ok=false`; panic; panic
- Điểm cộng: nil channel trong `select` để tắt case; bên gửi đóng

**9. `context` dùng để làm gì? Vì sao không truyền tham số qua `WithValue`?** (2.2)
- Ý phải có: huỷ, deadline, dữ liệu gắn với request; `WithValue` mất kiểu và che dependency
- Điểm cộng: huỷ chỉ có tác dụng khi code kiểm tra `Done()`; goroutine nền và `WithoutCancel`

**10. Channel hay mutex?** (1.4, 2.3)
- Ý phải có: channel để chuyển quyền sở hữu và điều phối; mutex để bảo vệ state
- Red flag: "Go luôn khuyên dùng channel"

**11. Vì sao `http.Get` nguy hiểm trong production?** (2.4)
- Ý phải có: client mặc định không timeout; goroutine và connection kẹt khi đối tác treo
- Điểm cộng: đóng và drain body; `MaxIdleConnsPerHost` = 2; retry có backoff chỉ với request idempotent

**12. `*sql.DB` là gì? Quên `rows.Close()` thì sao?** (2.5)
- Ý phải có: pool an toàn đồng thời; connection không về pool, pool cạn, request treo
- Điểm cộng: `MaxOpenConns` mặc định không giới hạn; dùng `db` thay `tx` trong transaction

**13. API trả `null` thay vì `[]` khiến app mobile crash.** (1.1, 2.5)
- Ý phải có: nil slice encode thành `null`; khởi tạo `[]T{}`
- Điểm cộng: `omitempty` và `omitzero`; test contract API

**14. Viết benchmark thế nào cho đúng?** (2.6)
- Ý phải có: `for b.Loop()` (1.24), `-benchmem`, chạy nhiều lần và so bằng `benchstat`
- Điểm cộng: vì sao `b.N` kiểu cũ dễ đo sai (setup, dead-code elimination)
- Red flag: đo bằng `time.Now()` một lần

**15. Test code có timeout và retry mà không làm test chậm?** (2.6)
- Ý phải có: `testing/synctest` với đồng hồ ảo; hoặc inject clock
- Điểm cộng: `synctest.Wait` chờ mọi goroutine block; `goleak` sau test

### 🔴 Senior

**16. Mô tả scheduler G-M-P. Goroutine gọi syscall blocking thì sao?** (3.1)
- Ý phải có: P giữ run queue, work stealing; syscall giữ M, P chuyển sang M khác; I/O mạng đi netpoller
- Điểm cộng: preemption bất đồng bộ; so với virtual thread của Java

**17. GC của Go hoạt động thế nào? `GOGC` và `GOMEMLIMIT` khác nhau ra sao?** (3.2)
- Ý phải có: concurrent mark-sweep, không thế hệ; `GOGC` theo tỉ lệ tăng heap, `GOMEMLIMIT` theo trần tuyệt đối
- Điểm cộng: Green Tea mặc định từ 1.26; thrash khi live heap sát limit

**18. Sau khi deploy lên k8s với limit 2 CPU, p99 tăng gấp đôi so với chạy trên VM.** (3.4)
- Ý phải có: `GOMAXPROCS` bằng số core node, bị CFS throttle; xem metric throttling
- Điểm cộng: Go 1.25+ tự theo cgroup (khi `go.mod` ≥ 1.25); automaxprocs cho bản cũ

**19. Service chạy vài ngày thì RAM tăng dần, số goroutine tăng theo.** (2.2, 3.3)
- Ý phải có: goroutine leak; pprof goroutine xem kẹt ở đâu; HTTP client không timeout, gửi channel sau timeout
- Điểm cộng: profile `goroutineleak` (1.27); `goleak` trong test; metric `NumGoroutine`

**20. Lỗi thỉnh thoảng `fatal error: concurrent map writes` và pod restart.** (1.1, 2.3)
- Ý phải có: map dùng chung không lock; không recover được; thêm mutex hoặc tách state
- Điểm cộng: chạy `-race` trong CI; `sync.Map` khi nào hợp
- Red flag: bọc `recover()` để chặn

**21. Thiết kế pipeline 3 stage có thể huỷ giữa chừng mà không leak goroutine.** (2.2)
- Ý phải có: mỗi stage `select` trên `ctx.Done()` khi gửi và nhận; bên gửi đóng channel; errgroup gom lỗi
- Điểm cộng: giới hạn đồng thời mỗi stage; test bằng `goleak`

**22. Service Go dùng quá nhiều RAM trong k8s.** (3.2, 3.3)
- Ý phải có: heap profile, tìm sub-slice giữ mảng lớn, map không co, cache không giới hạn; đặt `GOMEMLIMIT`
- Điểm cộng: phân biệt RSS với heap (runtime giữ lại bộ nhớ đã free); số goroutine
- Red flag: "tăng limit"
